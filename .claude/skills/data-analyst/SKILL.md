# 데이터 분석

숫자를 모으기 전에 **무엇을 알고 싶은지부터 정한다.**

## 순서를 뒤집지 않는다

❌ 로그를 잔뜩 쌓아두고 나중에 본다
✅ **질문을 먼저 적고**, 그 질문에 답하는 데 필요한 것만 기록한다

질문 없이 쌓은 로그는 아무도 안 본다. 그리고 개인정보만 늘어난다.

```
질문: 사람들이 몇 번째 단계에서 그만두나?
 → 필요한 것: 단계 진입 이벤트 하나
 → 필요 없는 것: 스크롤 위치, 체류 시간, IP
```

## 기록하지 않을 것 (기본값)

- IP 주소, User-Agent 원문
- 사용자가 입력한 본문 (검색어 정도는 예외로 검토)
- 이미 다른 표에서 조인으로 알 수 있는 값 (예: 이메일 — `user_id`로 충분하다)
- 화면 녹화, 히트맵 — 규모 대비 과하다

**"나중에 쓸지도 모르니까"는 기록할 이유가 아니다.**

## 이벤트 이름 규칙

`대상_행동` 으로 고정한다. 섞이기 시작하면 나중에 집계가 불가능해진다.

```
chapter_view    chapter_complete    prompt_copy    auth_signin
```

## 비용 분석

AI·외부 API를 쓰는 프로젝트라면 이게 제일 중요한 분석이다.

- **실제 호출만 센다.** 캐시로 재사용한 건 요금이 안 나갔으므로 세면 안 된다
- 기능별로 나눠 본다. 어느 기능이 비싼지 모르면 줄일 수도 없다
- 입력 토큰과 출력 토큰을 나눠 본다. 보통 출력이 훨씬 비싸다
- 사람당 사용량을 본다. 한 명이 튀면 그게 버그거나 오남용이다

## 해석할 때

- **표본이 작으면 말하지 않는다.** 사용자 3명의 완주율은 33%가 아니라 "아직 모른다"
- 숫자가 이상하면 먼저 **기록 코드를 의심한다.** 대개 사람 행동이 아니라 버그다
- 자동 호출(페이지 로드 시 실행되는 것)이 섞이면 모든 숫자가 부풀려진다

## 하지 않을 일

- 근거 없이 원인을 단정하지 않는다. "이탈이 늘었다"와 "이것 때문이다"는 다르다
- 사용자가 적을 때 대시보드를 만들지 않는다. **직접 물어보는 게 빠르고 정확하다**
