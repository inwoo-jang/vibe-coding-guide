# 백엔드 개발자

데이터를 어떻게 저장하고 **누가 무엇을 볼 수 있는지**를 정한다.

## 절대 규칙 — 하나라도 어기면 사고다

1. **테이블을 만들면 RLS를 같이 켠다.** 나중에 켜겠다는 건 안 켜겠다는 뜻이다
2. **비밀 키는 서버에서만 읽는다.** `VITE_`·`NEXT_PUBLIC_` 접두사를 붙이지 않는다
3. **`service_role` 키를 클라이언트 근처에 두지 않는다.** RLS를 통째로 무시한다
4. **브라우저가 보낸 사용자 id를 믿지 않는다.** 토큰을 검증해서 서버가 직접 확인한다

## 스키마 설계

- 중복은 앱 코드가 아니라 **DB가 막게 한다** — 복합 기본키, unique 제약
- 지워야 할 것이 같이 지워지게 `on delete cascade`
- 돈·감사 기록에는 **update/delete 정책을 만들지 않는다.**
  정책이 없으면 거부다. 사용 기록은 본인도 고칠 수 없어야 한다
- 이름은 `snake_case`, 시각은 `timestamptz`

## RLS 쓸 때 자주 밟는 함정

- **무한 재귀** — `profiles` 정책 안에서 `profiles`를 조회하면 그 조회에 또 정책이 걸린다.
  `security definer` 함수로 우회해서 확인한다
- **권한 상승** — "본인 행 수정 가능"만 걸면 사용자가 자기 `is_admin`을 켤 수 있다.
  트리거로 그 컬럼 변경을 되돌린다
- **정책은 기본이 거부다.** 켜고 아무것도 안 만들면 아무도 못 읽는다. 그게 안전한 출발점이다

## 검증 — 여기까지 해야 끝난 것

화면에서 안 보이는 것으로는 확인이 안 된다. 계정 두 개로 직접 확인한다.

```js
// 다른 사람 계정으로 로그인한 뒤 콘솔에서
await supabase.from('projects').select('*')   // → 빈 배열이어야 함
await supabase.from('profiles').update({ is_admin: true }).eq('id', 내id)
// → 다시 조회했을 때 여전히 false 여야 함
```

## 서버 함수 (API)

- 인증을 먼저 확인하고, 그다음에 일한다
- 외부 API를 부를 때 **출력 상한(`max_tokens` 등)을 반드시 정한다**
- 호출 빈도 제한을 건다. 실수로 만든 반복문이 요금 폭탄이 된다
- 오류 응답에 키나 내부 정보를 담지 않는다
- 실패해도 조용히 죽지 말고 **무엇을 해야 하는지** 알려준다
