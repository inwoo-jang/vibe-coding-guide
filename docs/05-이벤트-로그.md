# 이벤트 로그 설계 (아직 켜지 않음)

작성 2026-08-03 · 상태: **설계만. 구현 안 함** · 도입 조건 아래 참고

## 지금 안 켜는 이유

사용자가 3명이다. **로그를 보는 것보다 직접 물어보는 게 빠르고 정확하다.**
지금 켜면 (1) 개인정보를 모으고 (2) 유지할 코드가 늘고 (3) 아무도 안 보는 대시보드가 생긴다.

그런데 **나중에 켜려고 할 때 제일 아쉬운 건 과거 데이터**다.
그래서 코드는 안 짜되 **무엇을 남길지는 지금 정해둔다.** 이 문서가 그 정의다.

## 도입 조건 (하나라도 걸리면 켠다)

- 월 방문자 30명 이상 — 개별 대화로 파악이 안 되는 규모
- "몇 번째 챕터에서 사람들이 그만두나?"가 실제로 궁금해지는 시점
- 챕터가 15개를 넘어 어떤 챕터가 안 읽히는지 감이 안 잡힐 때

## 무엇을 답하고 싶은가 (질문이 먼저, 스키마는 그다음)

| # | 질문 | 필요한 이벤트 |
|---|---|---|
| Q1 | 사람들이 **몇 번째 챕터에서 그만두나** | `chapter_view` |
| Q2 | 프롬프트를 **실제로 복사해서 쓰나** | `prompt_copy` |
| Q3 | 완료 체크를 **누르긴 하나** (읽고 그냥 나가나) | `chapter_complete` |
| Q4 | 한 챕터에 **얼마나 머무나** (너무 길지 않나) | `chapter_view` + `dwell_ms` |
| Q5 | **로그인까지 가는 사람**이 몇 %인가 | `auth_signin` |
| Q6 | 용어 사전에서 **뭘 검색하나** (설명이 부족한 개념) | `glossary_search` |

Q6이 제일 값싸고 유용하다. 검색어는 "내가 안 쓴 챕터"의 목록이다.

## 이벤트 스키마

```sql
create table public.events (
  id          bigint generated always as identity primary key,
  user_id     uuid references public.profiles(id) on delete set null,  -- 비로그인은 null
  session_id  text not null,        -- 브라우저 세션 단위 무작위 id (비로그인 추적용)
  name        text not null,        -- 아래 목록 중 하나
  props       jsonb not null default '{}',
  created_at  timestamptz not null default now()
);

create index on public.events (name, created_at desc);
create index on public.events (user_id, created_at desc);
```

RLS: **insert만 anon에게 허용, select는 관리자만.** 남의 활동 로그가 읽히면 그 자체가 사고다.

### 이벤트 목록

| `name` | 언제 | `props` |
|---|---|---|
| `chapter_view` | 챕터 화면 진입 | `{ chapter_id }` |
| `chapter_dwell` | 챕터 화면 이탈 | `{ chapter_id, ms }` |
| `chapter_complete` | 완료 체크 켬 | `{ chapter_id }` |
| `chapter_uncomplete` | 완료 체크 끔 | `{ chapter_id }` |
| `prompt_copy` | 복사 버튼 | `{ chapter_id, label }` |
| `glossary_search` | 검색어 입력 (디바운스 후) | `{ q }` |
| `prompt_search` | 검색어 입력 (디바운스 후) | `{ q }` |
| `auth_signin` | 로그인 성공 | `{ method: 'magiclink' }` |

이름은 **`대상_행동`** 으로 고정한다. 섞이기 시작하면 나중에 집계가 지옥이 된다.

## 남기지 않는 것 (의도적으로)

- **IP 주소, User-Agent 원문** — 필요 없고, 필요해지면 그때 동의를 받는다
- **검색어 외의 사용자 입력** — 프롬프트에 붙여 쓴 내용은 절대 서버로 보내지 않는다
- **이메일을 `props`에 넣기** — `user_id`로 조인하면 된다. 같은 정보를 두 곳에 두지 않는다
- **화면 녹화, 히트맵** — 대상 규모 대비 과하다

## 구현할 때의 형태 (미리 정해둠)

`src/lib/analytics.js` 파일 하나. 화면은 이것만 부른다.

```js
// track('chapter_view', { chapter_id: 'setup' })
export function track(name, props = {}) { ... }
```

- **`.env`에 로그 설정이 없으면 아무것도 안 한다** (no-op). 로컬 개발이 로그로 더러워지지 않게
- 실패해도 조용히 넘어간다. **로그 때문에 화면이 깨지면 안 된다**
- `progress.js`와 같은 원칙: 화면은 `track()`만 알고, 뒤에 뭐가 있는지 모른다

## 세 줄 요약

1. 지금은 안 켠다. 사람이 적을 땐 물어보는 게 낫다
2. 켤 때는 위 8개 이벤트로 시작한다. 늘리는 건 나중에 쉽고, 줄이는 건 어렵다
3. 진입점은 `track()` 하나. 화면 코드에 Supabase를 직접 부르지 않는다
