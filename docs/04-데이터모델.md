# 데이터 모델

작성 2026-08-03 · 실행 가능한 SQL 원본: [`supabase/schema.sql`](../supabase/schema.sql)

이 문서와 SQL이 어긋나면 **SQL 파일이 정답**이다. 스키마를 바꾸면 둘 다 고친다.

## 왜 Supabase(Postgres)인가

가이드에 "테이블 설계"와 "RLS 보안" 챕터가 있다.
**가르치는 내용과 이 저장소의 실제 코드가 1:1로 맞아떨어져야** 예제로 쓸 수 있다.
그래서 SQL을 쓰는 Postgres여야 한다. → [06-결정-로그.md](06-결정-로그.md) D-002

## 테이블

### `profiles`

`auth.users`(Supabase가 관리하는 인증 테이블)에 우리가 붙이는 정보.
인증 테이블은 직접 수정하지 않는 게 원칙이라 별도 테이블로 둔다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | `uuid` PK | `auth.users.id`와 동일. FK, 사용자 삭제 시 함께 삭제 |
| `email` | `text` | 관리자 화면에서 누구인지 알아보려고 복사해 둔다 |
| `is_admin` | `boolean` | 기본 `false`. **본인이 못 바꾼다** (아래 정책 참고) |
| `created_at` | `timestamptz` | 가입 시각 |

### `projects`

이 가이드의 중심 단위. 사용자가 만들려는 것 하나.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | `uuid` PK | |
| `user_id` | `uuid` | `profiles.id` FK |
| `name` | `text` | 프로젝트 이름 |
| `one_liner` | `text` | 한 문장 요약 |
| `idea` | `text` | 사용자가 처음 적은 아이디어 원문 |
| `prd` | `jsonb` | AI가 뽑은 기획서 통째로 |
| `created_at` / `updated_at` | `timestamptz` | |

**`prd`를 컬럼으로 쪼개지 않고 `jsonb`로 둔 이유:** 기획서 항목은 앞으로 자주
바뀔 값이다. 바뀔 때마다 마이그레이션을 하느니 통째로 담는다. 대신 이 안의 값으로
검색하거나 집계할 일은 없다고 못 박아 둔다 — 그럴 일이 생기면 그때 쪼갠다.

### `progress`

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `project_id` | `uuid` | `projects.id` FK |
| `user_id` | `uuid` | `profiles.id` FK |
| `chapter_id` | `text` | `chapters.js`의 `id` (`setup`, `planning`, …) |
| `done` | `boolean` | 완료 여부 |
| `updated_at` | `timestamptz` | 마지막 변경 시각. 완료 날짜 표시에 쓴다 |

기본키는 `(project_id, chapter_id)` 복합키. **한 프로젝트의 같은 챕터에 두 줄을
만들 수 없다.** 이것 하나로 중복 체크 로직이 통째로 사라진다 — 앱에서 막지 말고
DB에서 막는다.

`user_id` 는 `project_id` 로 따라갈 수 있는데도 따로 둔다. RLS 정책과 "내 진도
전체" 조회가 조인 없이 끝나기 때문이다. 중복이지만 의도한 중복이다.

### `chapter_id`를 FK로 걸지 않는 이유

챕터는 지금 `src/data/chapters.js`에 있고 DB에 없다. 그래서 그냥 `text`다.
나중에 `chapters` 테이블을 만들면 그때 FK를 건다 → [02-기능범위.md](02-기능범위.md) "챕터 CMS".
그 전까지는 **`chapters.js`에서 `id`를 바꾸면 그 챕터의 진도가 끊긴다.** id는 바꾸지 말 것.

## RLS 정책

두 테이블 모두 RLS를 **켠다**. 켜기만 하고 정책을 안 만들면 아무도 아무것도 못 읽는다(기본 거부).
그게 안전한 기본값이다 — 정책을 하나씩 열어준다.

| 테이블 | 누가 | 무엇을 |
|---|---|---|
| `profiles` | 본인 | 자기 행 읽기 / 수정 / 생성 |
| `profiles` | 관리자 | 전체 행 읽기 |
| `projects` | 본인 | 자기 행 전부 (읽기/쓰기/수정/삭제) |
| `projects` | 관리자 | 전체 행 읽기 |
| `progress` | 본인 | 자기 행 전부 |
| `progress` | 관리자 | 전체 행 읽기 |

### 두 가지 함정

**1. `is_admin`을 본인이 못 바꾸게 해야 한다.**
"본인 행 수정 가능"만 걸면 사용자가 자기 `is_admin`을 `true`로 바꿔 관리자가 된다.
`schema.sql`에서 트리거로 막는다. 권한 상승(privilege escalation)이라고 부르는, 흔하고 조용한 사고다.

**2. 관리자 정책이 자기 자신을 다시 조회하면 무한 재귀에 빠진다.**
`profiles` 정책 안에서 `profiles`를 `SELECT`하면 그 조회에 또 정책이 걸린다.
그래서 `is_admin()`을 `security definer` 함수로 만들어 RLS를 우회해 확인한다.

## 마이그레이션 순서

1. supabase.com에서 프로젝트 생성
2. `.env` 작성 (`.env.example` 복사) — `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`
3. Supabase 대시보드 SQL Editor에 [`supabase/schema.sql`](../supabase/schema.sql) 전체를 붙여넣고 실행
4. Auth 설정 → 이메일 매직 링크 켜기, Site URL에 로컬 주소와 배포 주소를 넣기
5. 본인 계정으로 한 번 로그인 → SQL Editor에서 `update public.profiles set is_admin = true where email = '<내 이메일>';`
6. `.env`가 채워지면 앱이 자동으로 서버 저장 모드로 뜬다 ([`src/lib/supabase.js`](../src/lib/supabase.js))

**`.env`는 절대 커밋하지 않는다.** `.gitignore`에 들어 있다.

## anon key는 공개돼도 되나

된다. 브라우저에 나가는 키라 숨길 수 없고, 숨기는 게 목적이 아니다.
**anon key로 무엇을 할 수 있는지를 RLS가 정한다.** 그래서 RLS를 안 켜면 anon key = 전체 DB 공개다.
절대 클라이언트에 두면 안 되는 건 `service_role` 키다. 이건 RLS를 통째로 무시한다.

전체 키 분류와 유출 대응은 [09-보안-키관리.md](09-보안-키관리.md)에 있다.

## 로컬 폴백

`.env.local`이 없으면 앱은 `localStorage` 모드로 뜬다 (로그인 없음, 이 브라우저에만 저장).
개발 중에 Supabase 없이도 화면이 돌아가야 하고, 친구가 클론했을 때 바로 실행돼야 하기 때문이다.
경계는 [`src/lib/projects.js`](../src/lib/projects.js)와
[`src/lib/progress.js`](../src/lib/progress.js) 두 파일 안에 있다.
